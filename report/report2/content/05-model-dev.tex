\section{Model development}
\label{sec:model-dev}
Model development trains a supervised multi-class classification classifier to predict game outcome. The business question that I was tackling is, if a player considers a given opening at their rating level, what outcome distribution should they expect? Labels include three possible outcomes of white win, black win or draw. 

\subsection{Tools used}
Airflow task "\texttt{train\_model}" which calls \texttt{lichess-models train} package. Inside the \codecite{code_train} code, I wrap a scikit-learn \parencite{sklearn} \texttt{Pipeline} which is combination with \codecite{code_features} helps in building a \texttt{ColumnTransformer} for numeric and categorical columns, After which a classifier uses the GridSearchCV and sklearn's train test split function. This package implements the following models which includes logistic regression, random forest, and histogram gradient boosting.

The best pipeline serialises to \texttt{artifacts/lichess\_models/\{run\_id\}/model.joblib}. After which this code snippet\codecite{code_evaluate} scores the hold-out split and logs metrics like accuracy, macro-F1, and confusion-friendly counts to MLflow. This code \codecite{code_register} publishes under the project name of \texttt{lichess-outcome-predictor} in MLflow. The MLflow stack \githubparencite{code_mlflow_compose} uses Postgres for metadata and artifacts storage inside MinIO artifacts bucket.

% \textbf{Metrics and reproducibility.} Hold-out evaluation logs accuracy and macro-F1; I watch both because class imbalance makes accuracy optimistic. MLflow stores the conda-free environment implicitly through pip requirements in the repo; I still note the git commit hash manually in run tags when experimenting. For coursework evidence, the combination of \texttt{model.joblib}, MLflow UI screenshots, and cited training code satisfies ``development of ML models'' better than a single accuracy number in this PDF.

% \textbf{Retrieval of training data.} Splits live under artefact paths returned by \texttt{split\_paths(month)} in \codecite{code_dataset}. Airflow passes \texttt{--month} or \texttt{--previous-month} consistently across tasks so training never points at the wrong shard. That sounds obvious, but mismatched month parameters caused a silent train-on-January / evaluate-on-February bug during one all-nighter I do not want to repeat.
